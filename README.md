# CarSharing

Сервис каршеринга для Бишкека: Go backend, React frontend, расчёты в кыргызских сомах (KGS).
Планируются электрические, бензиновые, дизельные, гибридные и газовые автомобили.

Репозиторий: [Alisher24/CarSharing](https://github.com/Alisher24/CarSharing) (public).

Работает начальный каркас: React получает данные от Go API, API проверяет PostgreSQL,
схему и PostGIS через сгенерированный OpenAPI-интерфейс, вход по email и паролю выдаёт
серверную сессию, а подключённые браузеры получают сигналы об изменениях через SSE.
Бронирование на 15 минут и уведомления о конце брони обслуживаются настоящими операциями.
Бронь превращается в поездку: её можно начать, поставить на паузу и продолжить, а сервер
публикует режим, длительности по режимам, начатые минуты и оценку суммы по ставкам брони.
Модельный парк действительно движется: симулятор раз в секунду продвигает модель, расходует
источники по профилю автомобиля и заканчивает поездку сам, когда запаса для продолжения не
остаётся. Счёт законченной поездки уходит письмом в почтовую заглушку: письмо появляется в
локальном ящике на `http://127.0.0.1:8025`, а не в браузере. Реальной внешней доставки нет —
ящик и есть получатель этой сборки.

## Локальный запуск

Нужны Git, Docker с Linux containers и Docker Compose v2.29 или новее.
На Windows используйте Docker Desktop с WSL2 и PowerShell. Go и Node на хосте
для основного запуска не нужны. Первая сборка требует интернета.
Образ PostGIS закреплён для `linux/amd64`; ARM потребует эмуляции и отдельно не проверен.

```sh
git clone https://github.com/Alisher24/CarSharing.git
cd CarSharing
```

Подготовьте настройки из корня проекта — в PowerShell:

```powershell
powershell -ExecutionPolicy Bypass -File scripts/setup.ps1
```

Либо в Linux/macOS:

```sh
sh scripts/setup.sh
```

Если Node 24.21 уже установлен, на любой платформе можно выполнить
`node scripts/setup.mjs`. Setup создаёт `.env` из шаблона и случайные пароли/внутренний
ключи в `.secrets/`. Значения не выводятся; повторный запуск сохраняет их и настройки.
Пароли ролей БД — `db_admin_password`, `db_app_password` и `mailstub_app_password`:
роль миграций, роль приложения и роль почтовой схемы. Отдельно создаются
`simulator_token`, `demo_control_token`, `mailstub_delivery_token`,
`mailstub_demo_token`, `cursor_hmac_key`, `mailstub_cursor_hmac_key` и
`demo_user_password`. Последний — пароль двух демоаккаунтов ручной проверки;
`cursor_hmac_key` подключён к API: под ним подписываются курсоры постраничного чтения
уведомлений. Ротация этого ключа делает выданные ранее курсоры недействительными — это
ожидаемое поведение. `simulator_token` и `demo_control_token` — по токену на возможность
внутренней поверхности: API принимает их, симулятор получает первый, демонстрационные команды —
второй, и оба они не являются сессией пользователя. `mailstub_delivery_token` получает worker:
под ним он доставляет письмо, и токена демонстрационного управления у него нет.
`mailstub_demo_token` — токен демонстрационного действия заглушки, а `mailstub_cursor_hmac_key`
подписывает курсоры ящика отдельно от курсоров API: курсор одного сервиса не принимается другим.
Установка, созданная до
появления нового секрета, требует его файла: создайте `.secrets/demo_user_password` из
32 случайных байт в hex либо запустите setup в чистом каталоге. При обновлении полной старой
установки `internal_token` сохраняется как `simulator_token`; прежний файл остаётся
локальной копией. Пароль роли почты, которой в такой установке ещё нет, setup создаёт сам,
а не требует восстановить его из резервной копии. Частичная миграция или потеря существующего
ключа вызывает ошибку,
а не незаметную замену оставшихся значений. Session authentication key появится вместе с входом.
При утрате секрета восстановите его из своей локальной копии: новый пароль не подходит
к существующему volume. На Unix каталог секретов имеет права 0700; на Windows доступ
определяется правами папки пользователя. Не размещайте локальные секреты в общедоступной папке.

```sh
docker compose up --build -d
docker compose ps
```

Откройте [приложение](http://127.0.0.1:8080). Главный экран — карта парка: она доступна
без входа, использует локальную демонстрационную схему Бишкека и работает без онлайн-тайлов
и внешних ключей. В шапке — вход и компактный индикатор связи браузера с API.
Если порт занят, измените `APP_PORT` в `.env` и повторите `up`.
Наружу опубликованы только frontend на `127.0.0.1:8080` и ящик почтовой заглушки на
`127.0.0.1:8025`; БД, API и внутренний слушатель заглушки доступны только внутри Compose.

Ящик — это то, где видно письмо со счётом. Откройте
[http://127.0.0.1:8025/api/v1/messages](http://127.0.0.1:8025/api/v1/messages): коллекция
отдаёт новые письма первыми, по 20 на страницу, с `next_cursor` для следующей; письмо целиком —
`http://127.0.0.1:8025/api/v1/messages/<id>`, и его текст показывается как обычный текст, без
разметки. Ящик анонимный и только на чтение: создать, изменить или удалить письмо через него
нельзя, и работает он лишь на loopback-адресе машины. В браузере приложения письмо не
показывается — это отдельный локальный слушатель.

Вошедшему доступно бронирование: в карточке свободного автомобиля кнопка «Забронировать на
15 минут» открывает подтверждение с автомобилем, ставками движения и паузы, бесплатным сроком
и предупреждением, что дневной лимит не возвращается. Подтверждение отправляет команду с ключом
идемпотентности; после ответа сервера над картой появляется панель «Текущая бронь» с оставшимся
временем, закреплёнными ставками, переходом к машине и отменой. Одна бесплатная бронь на аккаунт
в календарный день по Бишкеку: когда она использована, кнопка бронирования отключена, а панель
называет момент, когда лимит вернётся. Если ответ на команду потерян, панель предлагает повторить
её исходным ключом, пока не прошли сутки; после этого остаётся прочитать состояние.

БД хранится в named volume. `docker compose restart`, `docker compose stop` и
`docker compose down` сохраняют данные. **`docker compose down -v` удаляет данные**;
для обычной остановки используйте `docker compose down` без `-v`.

За минуту до конца брони появляется предупреждение: оно называет автомобиль, момент
окончания и оставшееся время, приходит по персональному сигналу и хранится на сервере,
поэтому перезагрузка страницы не создаёт второе и не показывает прочитанное как новое,
а действие «Прочитано» отмечает прочтение на сервере. После истечения, отмены или начала
поездки предупреждение перестаёт быть действующим; когда worker остановлен, предупреждение
создаёт само чтение приложения, поэтому конец брони виден и без него.

Бронь можно начать кнопкой «Начать поездку», а идущую поездку — поставить на паузу и продолжить.
Панель показывает режим и время в нём, длительности движения и паузы, ставки снимка брони и
оценку суммы, посчитанную сервером по начатым минутам. Время в режиме отсчитывается от
серверного момента, а не от часов браузера, поэтому возвращение в закрытую вкладку показывает
то, что записано в БД, а не то, на чём её оставили. Старт требует, чтобы бронь была
действующей, а хотя бы один источник автомобиля допускал начало движения; пауза и продолжение
энергию не проверяют.

Поездку можно завершить: кнопка «Завершить поездку» спрашивает подтверждение, а сервер решает,
допустимо ли окончание там, где стоит автомобиль, по своей подтверждённой телеметрии — клиент не
присылает ни координат, ни суммы. Окончание вне зоны обслуживания отвечает `OUTSIDE_SERVICE_ZONE`,
а на давно не подтверждённой позиции — `TELEMETRY_STALE`; в обоих случаях поездка продолжается и
тарифицируется. Успешное окончание одной транзакцией закрывает отрезок, переводит аренду в
`completed` и выставляет неизменяемый счёт с двумя строками — движение и пауза, — посчитанный по
ставкам снимка брони и начатым минутам. Панель показывает причину окончания и итог счёта. Повтор
команды с исходным ключом возвращает сохранённый ответ, а новый ключ для завершённой поездки —
существующий счёт, поэтому двух счетов на одну поездку не появляется.

Та же транзакция записывает письмо со счётом в очередь, и worker доставляет его в заглушку под
ключом `invoice:<id счёта>:issued`. Письмо описывает сохранённый счёт: причину окончания, момент,
итог в сомах и обе строки с минутами и ставками. Ключ уникален в таблице ящика, поэтому повтор
доставки — после потерянного ответа, рестарта worker или запуска второй его копии — отвечает
исходной квитанцией и второго письма не создаёт; отказ оплаты и её повтор письма не меняют.
Заглушка недоступна — задание остаётся в очереди с ошибкой и повтором, а письмо приходит ровно
одно после её возвращения.

Процессы backend — API, worker, почтовая заглушка и симулятор. API обслуживает HTTP и держит
соединение с БД, по которому получает опубликованные сигналы; worker доставляет очередь, снимает
истёкшие брони и чистит
хранение; заглушка принимает письма во внутреннем слушателе и показывает их в ящике; симулятор раз
в секунду вызывает закрытый тик и продвигает модельный парк. Их можно
останавливать и перезапускать по отдельности: `docker compose stop worker` не мешает API отвечать,
`docker compose stop mailstub` оставляет задания на письма в очереди с ошибкой, а
`docker compose --profile demo stop simulator` оставляет машины там, где их застал последний тик, —
незавершённые задания и состояние модели сохраняются в БД.

Симулятор не запускается вместе со стеком: запуск демонстрации — отдельное явное действие, как seed
и восстановление сценария. Без него парк стоит там, где его поставил seed, и ни одна машина не
расходует запас.

## Миграции, seed и проверки

Одноразовый сервис `migrate` автоматически применяет SQL-миграции после готовности
БД и перед запуском API. Повторный `up` безопасен. API использует отдельную роль без
superuser/DDL-прав; административный секрет подключён только к БД, миграциям и seed.
Соединение с БД без TLS предназначено только для локальной сети Compose.

```sh
docker compose run --rm migrate status
docker compose run --rm migrate up
docker compose --profile demo run --rm seed
docker compose --profile demo run --rm demo-scenario
docker compose --profile demo up --detach simulator
docker compose run --rm simulator -once
docker compose --profile demo run --rm democontrol set-energy-remaining \
  --vehicle 01994342-6ba7-7000-8000-000100000001 --source battery --remaining 20
```

Seed создаёт демонстрационный парк из 25 автомобилей (по пять электрических, бензиновых,
дизельных, гибридных и газовых), зону обслуживания, тариф, служебные демоаккаунты и
подготовленные брони и поездки. Он создаёт только отсутствующее: повторный seed и
`restart` не меняют остатки энергии, телеметрию и срок брони.

`demo-scenario` — отдельная явная команда: она возвращает весь объявленный демонстрационный парк —
позиции, остатки, связь, маршрут и признак обслуживания — и подготовленные аренды. Модель расходует
запас, пока машина едет, поэтому «поставить демонстрацию обратно» означает поставить обратно и те
машины, которые оставлены для ручной проверки бронирования: именно их чаще всего и увозят. Данные
обычных пользователей команда не трогает: если любую машину парка арендовал обычный пользователь,
команда целиком отказывается и ничего не изменяет.

`democontrol` — демонстрационные команды: одно присваивание значения за вызов, через закрытый
API и под отдельным токеном. Доступны `set-telemetry-state`, `set-position`,
`set-energy-remaining`, `mark-serviced` и `set-next-payment-outcome`; у каждой есть
`--action-id`, и повтор с ним воспроизводит исходный ответ, а изменённое тело с тем же
идентификатором отвечает `409 IDEMPOTENCY_CONFLICT`. Отдельная команда `drop-next-response`
принадлежит почтовой заглушке и вызывается под её собственным токеном: она вооружает потерю ответа
следующей доставки, поэтому письмо сохраняется, а ответ теряется — worker повторяет доставку и
получает исходную квитанцию. Это и есть способ увидеть одно письмо вместо двух:

```sh
docker compose --profile demo run --rm democontrol drop-next-response
```

`simulator -once [-tick-id <uuid>]`
продвигает парк ровно один раз — это и готовый пример вызова тика, и способ воспроизвести
потерянный ответ.

Обычный запуск не выполняет seed. Запуск команд без `APP_ENV=demo` отклоняется.
Автоматический откат схемы намеренно не предлагается; перед опасными миграциями
потребуется резервная копия.

- `GET /api/v1/health/ready` через frontend возвращает готовность, город, валюту, часовой пояс и UTC-время сервера с шестью дробными цифрами.
- `GET /api/v1/health/live` проверяет только процесс; readiness проверяет БД, схему и PostGIS.
- `GET /api/v1/vehicles`, `/api/v1/vehicles/{id}`, `/api/v1/zones` и `/api/v1/tariffs` доступны анонимно и не раскрывают владельца аренды.
- Состояние автомобиля выводится при каждом чтении из действующей аренды и пригодности; отдельной хранимой копии статуса нет.
- `POST /api/v1/reservations` бронирует свободный автомобиль на 15 минут: владелец берётся из сессии, ставки и момент — из БД, ключ `Idempotency-Key` делает повтор возвратом исходного ответа, а `server_time` и `request_id` в теле остаются моментом первой попытки. `POST /api/v1/reservations/{id}/cancel` возвращает бронь до срока, а после него фиксирует истечение и отвечает `409 RESERVATION_EXPIRED`.
- `GET /api/v1/me/current` отвечает `200` всегда: действующая аренда либо `kind: none`, время сервера и состояние дневного лимита с моментом восстановления. Просроченную бронь это чтение снимает само — механизм истечения тот же, что у worker, — поэтому освобождение машины не зависит от запущенного worker.
- Идемпотентные результаты команд хранятся в `idempotency_requests` не менее 24 часов после ответа и удаляются worker'ом по сроку хранения; откат транзакции не оставляет ни результата, ни задания в очереди.
- `GET /api/v1/events` — анонимный поток сигналов об изменениях машин, зон и тарифов; `GET /api/v1/me/events` — поток сигналов своей аренды для вошедшего пользователя. Оба сначала отправляют `retry: 3000` и `ready` с временем сервера, затем только идентификатор и версию изменившегося объекта; каждые 15 секунд идёт комментарий `: keepalive`. Повторов и журнала событий нет: пропущенный сигнал исправляет чтение REST.
- Worker — отдельный процесс: он доставляет задания из очереди `outbox`, одним проходом раз в секунду освобождает истёкшие брони и создаёт предупреждения о последней минуте, удаляет доставленные сигналы старше суток и результаты команд старше 24 часов. Очередь переживает остановку процесса: задание получает lease на 30 секунд, повторяет попытки с задержкой от 1 до 60 секунд и не отмечается успешным, пока не доставлено.
- `GET /api/v1/me/notifications` отдаёт уведомления владельца, новые первыми, с `limit` от 1 до 100 (по умолчанию 20), `server_time` и подписанным `next_cursor`; чужой, повреждённый или относящийся к другой операции курсор отвечает `400 INVALID_CURSOR`. `POST /api/v1/me/notifications/{id}/read` отмечает прочтение и повторяется идемпотентно; чужой идентификатор неотличим от несуществующего (`404`). Обе операции требуют сессии, а отметка прочтения — ещё `Origin` и `X-CSRF-Token`. Сервер не хранит текст: русское сообщение строит клиент по типу уведомления.
- `GET /api/v1/me/rides` отдаёт завершённые поездки владельца, новые первыми, с `limit` от 1 до 100 (по умолчанию 20) и подписанным `next_cursor`; `GET /api/v1/me/invoices` отдаёт его счета тем же способом, каждый вместе с состоянием оплаты. Историю образует завершённая аренда с начатой поездкой: отменённые, истёкшие и текущая аренда в неё не попадают. Ленты упорядочены по разным моментам — поездки по окончанию, счета по выставлению — и читаются как две независимые коллекции: сшивать их по `invoice_id` на клиенте нельзя, они разойдутся на второй странице. Чужой, повреждённый или относящийся к другой операции курсор отвечает `400 INVALID_CURSOR`, запрос без сессии — `401`.
- `GET /api/v1/me/invoices/{id}` отдаёт счёт одной поездки с состоянием его оплаты и неизменной причиной окончания (`user_finished` либо `energy_depleted` со списком пустых источников). Это чтение существует потому, что поездку может закончить сервис: результат открывается по уведомлению об окончании и после перезагрузки, и состояние оплаты читается заново, а не запоминается вкладкой. Чужой счёт неотличим от несуществующего (`404`).
- API раз в пять секунд подтверждает телеметрию парка в demo-профиле: оно публикует то, что держит модель, и подтверждает координаты и остатки вместе, а подтверждение повышает версию машины и записывается в очередь вместе с изменением.
- Симулятор — отдельный процесс: он раз в секунду вызывает `POST /internal/v1/simulation/tick` и продвигает весь парк одной транзакцией под общим порядком блокировок. Повтор `tick_id` возвращает сохранённый результат и не двигает модель второй раз, поэтому потерянный ответ стоит одного повторного запроса. Остановка симулятора оставляет машины там, где их застал последний тик, а обнаружение исчерпания ждёт возобновления обработки: его выполняют тик, команда аренды или чтение текущей аренды.
- Поездка, у которой кончился запас, заканчивается на первой микросекунде отсутствия пригодного источника: `ended_at` — фактический момент, счёт и уведомление выставляются моментом операции, а список пустых источников сохраняется вместе с окончанием. Автомобиль получает `service_required` и остаётся недоступным до явного обслуживания; пополнение запрет не снимает.
- При недоступной БД readiness возвращает безопасный `503 SERVICE_UNAVAILABLE` в общем JSON-формате ошибок. Все API-ответы имеют `X-Request-ID` и `Cache-Control: no-store`.
- Старые health URL удалены; planned endpoints и внешний `/internal` возвращают JSON `404 RESOURCE_NOT_FOUND`.
- Логи: `docker compose logs --tail=100 api worker mailstub simulator migrate postgres frontend`.

Задания, которые не удаётся доставить, остаются в очереди с числом попыток и последней ошибкой;
начиная с десятой неудачной попытки worker пишет об этом отдельной записью в логе. Посмотреть их:

```sh
docker compose exec -T postgres psql -U carsharing_migrator -d carsharing -c \
  "SELECT id, kind, resource_id, attempts, last_error, next_attempt_at
   FROM outbox WHERE completed_at IS NULL AND attempts >= 10 ORDER BY next_attempt_at"
```

Тот же запрос без условия `attempts >= 10` показывает всю недоставленную очередь; worker раз в
30 секунд пишет в лог `worker heartbeat` с числом доставленных и неудачных заданий, размером
очереди и возрастом самого старого задания.

После запуска, при наличии Node 24.21 на хосте:

```sh
node --test scripts/setup.test.mjs
node scripts/smoke.mjs
node --test --test-concurrency=1 "scripts/acceptance/*.test.mjs"
npm ci
npm run e2e:install   # один раз: загружает Chromium для браузерных проверок
npm run e2e
```

Smoke проверяет реальные API/PostGIS, права роли, повтор миграций/seed и сохранность
данных, доступность публичного каталога, отсутствие старых/planned маршрутов и закрытый
внешний internal API. Приёмочные наборы `fleet` и `scenario` проверяют парк, зону,
тариф, свежесть телеметрии, истечение брони и восстановление сценария на собранном стеке;
`events` проверяет кадры и рукопожатие SSE, доставку изменения подключённому клиенту в
пределах двух секунд после commit, приватность двух потоков, закрытие персонального потока
при отзыве сессии, сохранность задания при остановленном worker, lease, повторы, диагностику
и очистку по сроку хранения. `reservations` проверяет само бронирование: гонки двух аккаунтов
за одну машину и одного аккаунта за две, дневной лимит и его границу по Бишкеку, отмену и её
гонку с истечением, чтение текущего состояния при остановленном worker, повтор команды с
исходным ключом после потери ответа, рестарта и смены сессии, конфликт отпечатка и отсутствие
следов у отката. Четыре момента срока брони проверяет `warnings`: до последней минуты
предупреждения нет, в неё создаётся ровно одно, в последний момент оно ещё действует, а на сроке
бронь освобождается и предупреждение перестаёт быть действующим. Тот же набор проверяет простой
и возврат worker, двух worker и отсутствие запоздалого предупреждения. `notifications` проверяет
обе операции уведомлений: только владелец, порядок и обе страницы пагинации, отказы курсоров,
идемпотентную отметку прочтения и 401/403/404. `signals` измеряет доставку персонального
`notification.changed`: владельцу в пределах двух секунд после сохранения предупреждения, ни
другому аккаунту, ни публичному потоку. `rides` проверяет переходы поездки по реальному HTTP:
старт, паузу и продолжение, ровно один открытый отрезок и совпадение границ после каждой команды,
повтор команды с исходным ключом и его заголовок, отказ повтора в достигнутой стадии без лишнего
отрезка, гонки старта с истечением, прогресс против строк БД и два отказа старта — просроченная
бронь и непригодный автомобиль. `finishing` проверяет окончание: завершённую поездку с закрытым
отрезком и причиной, счёт против сумм из `ride_segments` и ставок аренды, повтор с исходным ключом
и повтор с новым, две одновременные команды с одним счётом, границу зоны и точку снаружи,
устаревшую позицию, отказы 401/404/409 и освобождение автомобиля для другого аккаунта.
`simulation` проверяет модельный парк: повтор тика с тем же `tick_id` воспроизводит ответ и не
расходует запас второй раз, поездка с исчерпанным запасом заканчивается сама с причиной
`energy_depleted`, одним счётом, отчётом с фактическим моментом окончания и `service_required`,
окончание обнаруживается чтением текущей аренды при остановленном симуляторе, позднее обнаружение
тарифицируется до момента исчерпания, повтор демонстрационной команды воспроизводит ответ и
конфликтует при изменённом теле, а две копии симулятора дают одно окончание. Наборы
намеренно ждут реального времени и занимают несколько минут.
Он кратко останавливает БД и запускает её снова, проверяя ответ 503 и восстановление
API, поэтому выполняйте его в свободном локальном окружении. Для другого порта:
`node scripts/smoke.mjs http://127.0.0.1:8181`.

Браузерные проверки (`npm run e2e`) идут по тому же адресу и открывают два независимых
контекста браузера: один проверяет, что изменение, зафиксированное в БД, появляется во втором
клиенте в пределах двух секунд после commit (периодическая сверка на этой странице отключена
параметром адреса `?reconcile=off`, штатный интервал приложения это не меняет), другой — что
при оборванном потоке карта продолжает работать, показывает «Обновления задерживаются» и
восстанавливает изменение сверкой. `reservations.spec.mjs` проверяет бронирование в браузере:
один клиент бронирует машину через подтверждение, второй видит её занятой по сигналу, затем
отмену и освобождение; панель возвращается после перезагрузки и переживает закрытие карточки и
панели аккаунта; использованный дневной лимит отключает кнопку бронирования и называет момент
восстановления. `notifications.spec.mjs` проверяет предупреждение в браузере: оно появляется
один раз в последнюю минуту (в проверке доставки сверка отключена тем же параметром), называет
машину, срок и оставшееся время, переживает перезагрузку и не показывается новым после
«Прочитано», перестаёт быть действующим на сроке и при отмене, а без сигнала восстанавливается
штатной сверкой.

## Адреса интерфейса

Интерфейс имеет адреса, а не одну страницу: `/` — карта и текущая аренда, `/account` ведёт к
`/account/rides` (лента поездок), `/account/invoices` — лента счетов, `/account/invoices/{id}` —
один счёт. Ссылка на счёт пересылается и переживает перезагрузку; глубокая ссылка отдаётся
статикой (`try_files $uri $uri/ /index.html` в `infra/nginx.conf`). Кнопка в шапке одна: «Вход»
без сессии открывает форму на карте, «Кабинет» с сессией ведёт в кабинет, где живут адрес
аккаунта и «Выйти». Адрес кабинета, открытый без сессии, показывает ту же форму входа на месте
ленты и сохраняет адрес: после входа человек остаётся там, куда шёл. Почему маршрутизатор не
берёт на себя загрузку данных — [ADR 0003](docs/adr/0003-account-navigation.md).

## Разработка

React с hot reload, с тем же API и БД:

```sh
docker compose -f compose.yaml -f compose.dev.yaml up --build -d
```

Адрес остаётся [127.0.0.1:8080](http://127.0.0.1:8080); изменения в `frontend/src`
подхватываются автоматически. Изменения зависимостей требуют пересборки. Возврат
к собранному frontend: `docker compose up --build -d`. Backend пересобирается той же
командой; автоматический Go hot reload пока не включён.

Для проверок без контейнерной сборки нужны Go 1.27.1 и Node 24.21.0 с npm:

```sh
go -C backend test ./...
go -C backend vet ./...
npm ci
npm run format:check
npm --prefix frontend ci
npm --prefix frontend run build
```

Форматирование и линт стилей обязательны для каждого изменения; правила чтения кода
описаны в `AGENTS.md`. Prettier выравнивает TypeScript, JavaScript, CSS и JSON,
Stylelint проверяет CSS, `gofmt` — Go. Хук `pre-commit` форматирует файлы из индекса
той же конфигурацией, а `npm run format` выравнивает репозиторий целиком.
Сгенерированный код исключён из форматирования: он обновляется только генерацией.

Версии Go/Node и образы закреплены в Dockerfiles/Compose, зависимости — в
`go.mod`/`go.sum` и `package-lock.json`. Использованы React 19.3, react-router 7.11,
TypeScript 7.0, Vite 8.3, chi 5.3, pgx 5.11 и goose 3.28. [Vite поддерживает Node 24](https://vite.dev/guide/),
[PostGIS использует путь volume PostgreSQL 18](https://github.com/postgis/docker-postgis).
Обязательный Repository checks параллельно проверяет форматирование и стили,
Go, TypeScript-сборку, воспроизводимость контрактов, npm/Go-зависимости, историю
секретов и полный Compose smoke с тестовой PostGIS. Итоговый check проходит только
при успехе всех этих задач.

## Учётные записи и сессии

Вход по email и паролю. Сессия хранится в PostgreSQL, браузер получает только непрозрачный
токен в cookie `carsharing_session` (`HttpOnly`, `Path=/`, `SameSite=Lax`, абсолютные 12 часов
без продления); в БД лежит его SHA-256. `Secure` включается через `SESSION_COOKIE_SECURE=true`
и выключен только в документированном локальном HTTP-профиле. Создание пользователя и сохранение
сессии выполняются одной транзакцией: откат не оставляет ни пользователя, ни сессии.

Мутации учётной записи проверяют `Origin` по списку `ALLOWED_ORIGINS`; мутации с действующей
сессией дополнительно проверяют `X-CSRF-Token` из снимка сессии. CSRF-токен выдаётся на каждую
новую сессию и не действует дольше неё.

### Параметры Argon2id и измерения

Пароли хэшируются Argon2id с индивидуальной солью. Параметры — конфигурация, а не константы:

| Настройка | Переменная | Значение |
| --- | --- | --- |
| Память | `AUTH_ARGON2_MEMORY_KIB` | 19456 KiB (19 MiB) |
| Проходы | `AUTH_ARGON2_PASSES` | 2 |
| Потоки | `AUTH_ARGON2_PARALLELISM` | 1 |
| Одновременных вычислений на экземпляр | `AUTH_ARGON2_CONCURRENT` | 2 |

Измерение в целевом Docker-окружении (образ сборки `golang:1.27.1-alpine`, `linux/amd64`,
11th Gen Intel Core i7-11800H @ 2.30GHz), команда
`go test ./internal/auth/ -run NONE -bench BenchmarkDeployedHashing -benchtime 20x -cpu 1`:

| Величина | Результат |
| --- | --- |
| Время одного хэша | 28.4 мс |
| Память на один хэш | 19.00 MiB |

При занятости обоих мест вычисления запрос получает `503 SERVICE_UNAVAILABLE` без постановки
в неограниченную очередь. Неизвестный email проверяется против фиктивного хэша, чтобы быстрый
ответ не раскрывал отсутствие аккаунта.

### Ограничения частоты

Счётчики хранятся в PostgreSQL и переживают restart. Применимое ограничение проверяется до
вычисления хэша, поэтому отклонённая попытка не оплачивает Argon2id. Превышение даёт
`429 RATE_LIMITED` с `Retry-After`; доступ восстанавливается сам по истечении окна.

| Операция | Область счётчика | Порог | Окно | Переменные |
| --- | --- | --- | --- | --- |
| Вход | email + IP | 10 неудач | 15 минут | `RATE_LIMIT_SIGNIN_EMAIL_ADDRESS_ATTEMPTS` / `_WINDOW` |
| Вход | email | 30 неудач | 15 минут | `RATE_LIMIT_SIGNIN_EMAIL_ATTEMPTS` / `_WINDOW` |
| Вход | IP | 100 попыток | 15 минут | `RATE_LIMIT_SIGNIN_ADDRESS_ATTEMPTS` / `_WINDOW` |
| Регистрация | IP | 10 попыток | 1 час | `RATE_LIMIT_REGISTRATION_ADDRESS_ATTEMPTS` / `_WINDOW` |

## Контракт API и генерация

Источник HTTP-схем — `openapi/public.yaml`, `openapi/internal.yaml` и
`openapi/mailstub.yaml` (OpenAPI 3.0.3), с общими схемами в `openapi/components/`.
Обслуживаются health, операции учётной записи, публичный каталог, оба потока сигналов,
бронирование с отменой, три команды поездки — старт, пауза и продолжение, — обе операции
уведомлений, чтение одного счёта и обе коллекции кабинета: завершённые поездки и счета.
Полные Go DTO/strict interfaces и public TypeScript SDK описывают и будущие функции;
их наличие не означает работающий endpoint, поэтому статус каждой операции указан в
спецификации через `x-implementation-status`. Для production health отдельно генерируется
интерфейс из того же public-контракта; потоки объявлены как `text/event-stream`, поэтому
сгенерированный ответ пишет кадры по мере их появления, а не собирает тело целиком.

Нужны Go 1.27.1 и Node 24.21.0 с npm. Из корня проекта:

```sh
npm ci
npm --prefix frontend ci
npm --prefix tools/openapi ci
npm --prefix tools/openapi run generate
npm --prefix tools/openapi run check
```

Корневой `npm ci` обязателен: `check` запускает frontend-сборку и проверки через npm
корня, поэтому без него последняя команда завершится ошибкой.

Закреплены `oapi-codegen 2.8.0`, Go runtime `1.6.0`, validation middleware `1.2.0`
и `@hey-api/openapi-ts 0.99.0`. Генератор TypeScript работает из отдельного
`tools/openapi` с compiler API TypeScript 6.0.3; frontend продолжает использовать
TypeScript 7.0.2. Fetch-клиент копируется из закреплённого генератора 0.99.0:
первоначально указанный standalone `@hey-api/client-fetch 0.13.1` несовместим с
генерируемыми им типами и SSE-методами. Это осознанное изменение инструментария T03.
Транзитивный `js-yaml` поднят через `overrides` до 4.3.2: версия из генератора
содержала известную уязвимость, найденную `npm audit`.

Generated-код в `backend/internal/contracts/*/generated.go` и
`frontend/src/shared/api/generated/` хранится в Git и не редактируется вручную.
Промежуточные локальные bundles находятся в игнорируемом `.tools/contracts/`.
Удалённые `$ref` не разрешаются. Команда `check` повторяет генерацию и требует
побайтово одинаковый результат, затем запускает Go tests/vet, проверки setup и
frontend typecheck/build. Если generated-файлы устарели, команда обновит их и
завершится ошибкой, чтобы изменения можно было просмотреть и закоммитить.

Проверки охватывают inventory endpoints, закрытые unions, примеры payloads, точные
числа, UUID, календарные даты, пагинацию и HTTP-ошибки. Позиционные ограничения
`x-coordinate-order` и `x-mode-order`, которые OpenAPI 3.0 не выражает через tuple,
проверяются дополнительным валидатором. Planned requests проверяются изолированным
test router; почтовая заглушка обслуживает все четыре свои операции — доставку,
демонстрационное действие и обе операции ящика, — а её пути разведены между двумя
слушателями расширением `x-listener` самого контракта.
После локальных проверок запустите отдельный Compose smoke из раздела выше:
он проверяет настоящую БД и не заменяется тестовой dependency check.

Это локальная версия для разработки. Конфигурация публичного развёртывания с HTTPS,
резервным копированием и реальными провайдерами в этот этап не входит.
Проверка Trivy от 12.09.2026 обнаружила известные CVE в базовом PostGIS и инструментах
сборки Go/Node. CI запускает `npm audit` и `govulncheck` как блокирующие проверки; разбор и
исправление системных пакетов контейнеров остаётся частью T18. Отсутствие находок этих сканеров не означает,
что всё окружение свободно от уязвимостей.
