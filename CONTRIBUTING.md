# Работа с репозиторием

## Локальная подготовка

Нужны Git и доступ к GitHub для загрузки Gitleaks. Команды ниже выполняются
из корня проекта в Git Bash на Windows x64 или в shell на Linux x86_64:

```sh
sh scripts/install-gitleaks.sh
git config --local core.hooksPath .githooks
```

Скрипт устанавливает Gitleaks 8.30.1 в игнорируемый каталог `.tools/` и проверяет
SHA-256 официального архива до распаковки. Глобальная установка не нужна.
Для других платформ установите эту версию в `PATH` из
[официального релиза](https://github.com/gitleaks/gitleaks/releases/tag/v8.30.1).
При обновлении версии замените версию и обе контрольные суммы в скрипте установки.

Hook подключается отдельно после каждого clone. Он проверяет индекс перед commit,
отказывает при отсутствии сканера и запрещает отслеживание игнорируемых файлов,
в том числе принудительно добавленного `docs/`. Это локальная проверка; обязательность
серверной проверки обеспечивается правилами GitHub.

## Задача и PR

1. Обновить `master`: `git switch master`, затем `git pull --ff-only`.
2. Создать ветку `git switch -c codex/Txx-short-name`.
3. Выполнить ограниченную задачу, добавить только нужные файлы в индекс.
4. Проверить `git diff --cached --check` и `sh scripts/check-secrets.sh staged`.
5. Создать commit, отправить рабочую ветку и открыть PR в `master`.
6. Описать результат, реальные проверки и ограничения в шаблоне PR.
7. После успешных проверок и просмотра изменений выполнить squash merge.
8. Обновить `master`, выполнить применимую smoke-проверку и начать следующую ветку.

Однократное исключение T00: минимальный начальный commit в пустом `master`,
чтобы рабочую ветку можно было сравнивать через PR. Остальная настройка T00 идёт
в `codex/T00-repository`.

## Исключённые файлы и секреты

Весь корневой `docs/` остаётся локальным, включая будущие вложенные файлы.
Не добавляйте его через `git add -f`. Инструкции, необходимые после clone,
хранятся в корневых README.md и CONTRIBUTING.md.

Локальные `.env*`, ключи, сертификаты, секретные конфиги, дампы, runtime-данные,
логи и тестовые артефакты исключены из Git и Docker-контекста. Шаблоны
`.env.example` и `.env.*.example` разрешены, но содержат только безопасные заглушки.
SQL-миграции, `go.sum` и lockfile frontend должны отслеживаться.
Используйте корень репозитория как Docker build context, чтобы применялся `.dockerignore`.

Перед отправкой ветки можно проверить всю локально доступную историю:

```sh
sh scripts/check-secrets.sh history
```

CI загружает полную историю и проверяет её Gitleaks, включая секреты,
удалённые последующим коммитом. Вывод секретов маскируется; отчёты с их содержимым
не публикуются. Сканер не заменяет просмотр diff. Если секрет попал в историю,
сначала отзовите его, затем устраните утечку; удаление строки не очищает историю.

## Настройки GitHub для T00

Целевая конфигурация после появления первого PR и его проверки:

- Основная ветка `master`; разрешён squash merge и удаление уже слитых веток.
- Обязательный PR; обязательная проверка `Repository checks` с актуальной базой.
- Закрытые обсуждения, запрет force push и удаления `master`, правила действуют на администратора.
- В одиночном проекте число обязательных одобрений — 0; требование PR сохраняется.
- Actions: минимальные разрешения `contents: read`; workflow не получает секреты приложения.
- Dependabot для GitHub Actions; Go, npm и Docker добавляются вместе с манифестами в T02.
- GitHub secret scanning и push protection включаются, если доступны репозиторию.

Это целевые настройки, а не доказательство их применения. Фактический статус T00
указывается в README.md. Доступность защиты зависит от видимости и тарифа:
[документация GitHub](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches).
Если серверная защита недоступна, процесс PR/CI сохраняется, а ограничение фиксируется явно.

Полный CI приложения (Go, TypeScript, БД, контракт и зависимости) относится к T04.
Workflow T00 проверяет только гигиену репозитория и секреты.
