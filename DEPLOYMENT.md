# Развёртывание

Путь от чистой машины до проверенной установки: подготовка, секреты, запуск, проверка того, что
развёрнуто, эксплуатация, резервная копия и восстановление. Разворачивается локальная сборка в
Docker Compose — единственная форма установки этой сдачи. Публичное размещение, HTTPS и реальные
провайдеры в неё не входят: границы названы в §9.

Корневой [README](README.md) описывает продукт и его поведение; этот файл — установку и её
обслуживание. Числа в §1.2 — измеренные на одной машине в прогоне T19, а не расчётные.

## 1. Требования

### 1.1 Программы

| Что | Версия | Зачем |
| --- | --- | --- |
| Git | любая поддерживаемая | получить исходники |
| Docker с Linux-контейнерами | проверялось на Engine 27.1.1 | вся установка работает в контейнерах |
| Docker Compose | v2.29 или новее | `compose.yaml` использует профили, секреты и условия готовности |
| Node с npm | 24.21.0 | **необязательно**: нужен на хосте только для smoke, приёмочных и браузерных проверок |

На Windows — Docker Desktop с backend WSL2; команды даны для PowerShell там, где они отличаются.
Go и Node для самого запуска не нужны: образы собираются внутри Docker.

Первая сборка требует интернета — загружаются базовые образы и зависимости. С T23 она ходит не
только в реестры пакетов: `frontend.Dockerfile` вырезает архив карты из закреплённой суточной
сборки Protomaps на `build.protomaps.com` и забирает шрифты и спрайты с
`protomaps.github.io/basemaps-assets`. Адреса объявлены один раз в
`frontend/src/features/map/basemap.json`; недоступность любого из них останавливает сборку с
названным адресом, а не даёт образ без карты. Готовые образы, как и прежде, работают без сети:
архив, шрифты и спрайты лежат внутри образа frontend и отдаются тем же nginx.
Образ PostGIS закреплён digest'ом для `linux/amd64`; на ARM потребуется эмуляция, и отдельно этот
случай не проверялся.

### 1.2 Ресурсы — измерено, а не оценено

Замер прогона T19 на Windows 11 (Docker Engine 27.1.1, Compose v2.29.1-desktop.1,
Intel i7-11800H, 15.8 ГиБ памяти). Ваша машина даст другие числа; порядок величин — этот.

| Величина | Наблюдённое | Чем измерено |
| --- | --- | --- |
| Первая сборка на пустом кэше | 98 с | `docker compose up --build -d` после `docker builder prune -af` |
| Повторная сборка без изменений | 4.5 с, все стадии `CACHED` | та же команда |
| Запуск на готовых образах | 29.7–32.3 с до готовности всех служб | `docker compose up -d` |
| Перезапуск | 16.0 с | `docker compose restart` |
| Пиковая память стека | 159.3 МиБ на восьми запущенных контейнерах | `docker stats --no-stream` |
| Образы | frontend 60.6 МБ, backend 97.7 МБ (один образ на все процессы backend) | `docker images` |
| Том с данными после демонстрации | 109.3 МБ | `docker run --rm -v carsharing_postgres_data:/data alpine du -sh /data` |
| Кэш сборки | 592.7 МБ после одной полной сборки | `docker system df` |

Свободные порты: `127.0.0.1:8080` для приложения (меняется настройкой `APP_PORT`) и
`127.0.0.1:8025` для ящика почтовой заглушки.

## 2. Установка

### Шаг 1. Получить исходники

```sh
git clone https://github.com/Alisher24/CarSharing.git
cd CarSharing
```

В клоне нет ни `.env`, ни `.secrets/`: настройки и секреты создаёт следующий шаг.

### Шаг 2. Настройка и секреты

Из корня проекта, в PowerShell:

```powershell
powershell -ExecutionPolicy Bypass -File scripts/setup.ps1
```

В Linux и macOS:

```sh
sh scripts/setup.sh
```

Обе обёртки запускают `scripts/setup.mjs` в закреплённом образе Node, поэтому Node на хосте не
нужен. Если Node 24.21 уже установлен, на любой платформе работает `node scripts/setup.mjs`.

Setup создаёт `.env` из `.env.example` и десять файлов секретов в `.secrets/`. Значения —
32 случайных байта в hex; в лог они не выводятся.

| Файл секрета | Кому выдан | Что защищает |
| --- | --- | --- |
| `db_admin_password` | `postgres`, `migrate`, `seed`, `demo-scenario` | роль `carsharing_migrator`: схема и миграции |
| `db_app_password` | `api`, `worker` | роль `carsharing_app` без прав DDL |
| `mailstub_app_password` | `mailstub` | роль `mailstub_app`: только схема почты |
| `cursor_hmac_key` | `api` | подпись курсоров постраничных чтений API |
| `mailstub_cursor_hmac_key` | `mailstub` | подпись курсоров ящика, отдельно от курсоров API |
| `simulator_token` | `api`, `simulator` | вызов внутреннего тика симуляции |
| `demo_control_token` | `api`, `democontrol` | демонстрационные команды внутренней поверхности |
| `mailstub_delivery_token` | `worker`, `mailstub` | доставка письма в заглушку |
| `mailstub_demo_token` | `mailstub`, `democontrol` | демонстрационная потеря ответа заглушки |
| `demo_user_password` | `seed` | пароль двух демоаккаунтов ручной проверки |

Правила обращения с секретами:

- **Повторный setup сохраняет действующие значения** и не перезаписывает их молча.
- **Потерянный секрет не заменяется новым.** Новый пароль не подходит к существующему тому БД:
  восстановите файл из своей локальной копии либо запускайте setup в чистом каталоге. Частичная
  потеря вызывает ошибку, а не тихую замену оставшихся значений.
- **Права.** На Unix каталог секретов имеет режим `0700`, файлы — `0444`, `.env` — `0600`; на
  Windows доступ определяется правами папки пользователя. Не размещайте каталог в общедоступной
  папке и не кладите секреты в облачную синхронизацию без шифрования.
- **Ротация `cursor_hmac_key` делает выданные ранее курсоры недействительными** — это ожидаемое
  поведение, а не отказ.
- Секреты попадают в контейнеры файлами через Compose secrets: в окружении процесса стоит только
  путь `*_FILE=/run/secrets/...`, самого значения там нет.

### Шаг 3. Сборка и запуск

```sh
docker compose up --build -d
```

```sh
docker compose ps
```

Порядок задан условиями готовности, а не задержками: `postgres` становится healthy, одноразовый
`migrate` применяет SQL-миграции и завершается с кодом 0, после этого поднимаются `api`, `worker`
и `mailstub`, а `frontend` ждёт готовности API. Повторный `up` безопасен: миграции идемпотентны.

Запуск без профиля `demo` поднимает пять постоянных служб: `postgres`, `api`, `worker`, `mailstub`,
`frontend`. Симулятор и демонстрационные данные — отдельное явное действие (шаг 5).

### Шаг 4. Проверка того, что развёрнуто

Минимальная проверка, не требующая Node на хосте:

| Что проверяется | Команда или адрес | Ожидаемое |
| --- | --- | --- |
| Все службы подняты | `docker compose ps` | пять служб `running`, `migrate` — `exited (0)` |
| Процесс жив | `curl http://127.0.0.1:8080/api/v1/health/live` | `200` |
| БД, схема и PostGIS готовы | `curl http://127.0.0.1:8080/api/v1/health/ready` | `200`, город, валюта, часовой пояс и время сервера |
| Приложение открывается | <http://127.0.0.1:8080> | карта парка, доступная без входа |
| Ящик почты открывается | <http://127.0.0.1:8025> | страница ящика со списком писем, на чистой установке пустым |
| Внутренняя поверхность закрыта | `curl -i http://127.0.0.1:8080/internal/v1/simulation/tick` | `404 RESOURCE_NOT_FOUND` |

Полная проверка, если на хосте есть Node 24.21:

```sh
node scripts/smoke.mjs
```

Smoke проверяет реальные API и PostGIS, права роли БД, повтор миграций и seed, сохранность данных,
доступность публичного каталога и закрытость внешнего `/internal`. **Он кратко останавливает БД**,
чтобы увидеть ответ `503` и восстановление, поэтому выполняйте его в свободном локальном окружении.
В прогоне T19 — `PASS` за 15.3 с. Для другого порта: `node scripts/smoke.mjs http://127.0.0.1:8181`.

Приёмочные наборы и браузерные проверки описаны в README, раздел «Миграции, seed и проверки»; они
занимают несколько минут, потому что намеренно ждут реального времени.

### Шаг 5. Демонстрационные данные — необязательный шаг

Обычный запуск демонстрацию не ставит. Каждая команда ниже — отдельное явное действие, и все они
требуют профиля `demo` (`APP_ENV=demo` уже задан в `compose.yaml`; без него команды отклоняются).

```sh
docker compose --profile demo run --rm seed
```

```sh
docker compose --profile demo up --detach simulator
```

`seed` создаёт парк из 25 автомобилей, зону обслуживания, тариф, демоаккаунты и подготовленные
аренды. Он идемпотентен: повтор не меняет остатки энергии, телеметрию и сроки броней.

`simulator` — часы модельного парка: раз в секунду он продвигает модель. Пока он не запущен, ни одна
машина не расходует запас, и это ожидаемое состояние, а не отказ. Остановка оставляет машины там,
где их застал последний тик.

Ещё две демонстрационные команды:

```sh
docker compose --profile demo run --rm demo-scenario
```

```sh
docker compose --profile demo run --rm democontrol set-energy-remaining --vehicle 01994342-6ba7-7000-8000-000100000001 --source battery --remaining 20
```

`demo-scenario` возвращает объявленный демонстрационный парк в исходное состояние; если любую
машину парка арендовал обычный пользователь, команда целиком отказывается и ничего не меняет.
`democontrol` выполняет одно присваивание значения за вызов через внутренний API под своим токеном.

Пароль демоаккаунтов лежит в `.secrets/demo_user_password` и нигде не печатается:

```sh
cat .secrets/demo_user_password
```

```powershell
Get-Content .secrets/demo_user_password
```

## 3. Что опубликовано наружу

| Адрес | Служба | Доступ |
| --- | --- | --- |
| `127.0.0.1:8080` (`APP_PORT`) | `frontend` | приложение и `/api` через proxy |
| `127.0.0.1:8025` | `mailstub` | ящик почтовой заглушки, анонимный и только на чтение |

Больше не публикуется ничего: БД, API, worker и внутренний слушатель заглушки доступны только внутри
сети Compose. Proxy отвечает на любой путь под `/internal` ответом `404`, поэтому внутренняя
поверхность недостижима снаружи даже с правильным токеном. Соединение с БД идёт без TLS и
предназначено только для внутренней сети Compose.

## 4. Настройки

Единственный файл настроек установки — `.env`; в нём по умолчанию опубликованный порт и четыре
значения лимитов, которые локальная приёмка передаёт тому же процессу, что и Compose.
Compose подставляет из `.env` и из окружения оболочки только те переменные, которые объявлены в
`compose.yaml`. Настройка, которой там нет, меняется правкой `compose.yaml` — это сознательная
граница: список того, что установка разрешает менять снаружи, виден в одном файле.

| Настройка | Значение по умолчанию | Где объявлена | Что меняет |
| --- | --- | --- | --- |
| `APP_PORT` | `8080` | `.env` и `compose.yaml` | опубликованный порт приложения |
| `APP_ENV` | `production` в коде, `demo` в `compose.yaml` | `compose.yaml` | профиль: только `demo` допускает seed и демонстрационные команды |
| `HTTP_ADDR` | `:8080` | код | слушатель процесса внутри контейнера |
| `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER` | `postgres`, `5432`, `carsharing`, `carsharing_app` | `compose.yaml` | подключение к БД; роль у каждого процесса своя |
| `ALLOWED_ORIGINS` | `http://127.0.0.1:<APP_PORT>`, `http://localhost:<APP_PORT>` | `compose.yaml`, из `APP_PORT`; вне Compose — код | origin, с которых принимается изменяющий запрос |
| `SESSION_COOKIE_SECURE` | выключено | код | `Secure` у cookie сессии; `true`, `TRUE`, `1` включают, `false`, `0` выключают |
| `AUTH_ARGON2_MEMORY_KIB`, `_PASSES`, `_PARALLELISM` | `19456`, `2`, `1` | код | стоимость одного хеша пароля |
| `AUTH_ARGON2_CONCURRENT` | `2` | код | сколько проверок пароля идут одновременно |
| `RATE_LIMIT_SIGNIN_EMAIL_ADDRESS_ATTEMPTS`, `_WINDOW` | `10`, `15m` | код; локальный экспорт `.env` | бюджет входа по паре «почта и адрес» |
| `RATE_LIMIT_SIGNIN_EMAIL_ATTEMPTS`, `_WINDOW` | `30`, `15m` | код; локальный экспорт `.env` | бюджет входа по почте |
| `RATE_LIMIT_SIGNIN_ADDRESS_ATTEMPTS`, `_WINDOW` | `100`, `15m` | код; локальный экспорт `.env` | бюджет входа по адресу |
| `RATE_LIMIT_REGISTRATION_ADDRESS_ATTEMPTS`, `_WINDOW` | `10`, `1h` | код; локальный экспорт `.env` | бюджет регистраций с адреса |
| `MAILSTUB_INBOX_ADDR` | `:8025` | код | слушатель ящика заглушки |
| `INTERNAL_API_URL` | адрес API внутри сети Compose | `compose.yaml` | куда обращаются симулятор и демонстрационное управление |
| `*_FILE` | пути в `/run/secrets` | `compose.yaml` | файлы секретов; сами значения в окружении не появляются |

Изменение опубликованного порта — строка `APP_PORT=8181` в `.env` и повторный запуск:

```sh
docker compose up -d
```

Разрешённый список origin при этом меняется вместе с портом: `compose.yaml` объявляет
`ALLOWED_ORIGINS` из того же `APP_PORT`, поэтому вход, бронь и оплата продолжают отвечать, а не
отказывать с `403 ORIGIN_NOT_ALLOWED`. Согласованность порта в `compose.yaml`, `.env.example` и в
коде проверяет `node --test scripts/published-port.test.mjs` — проверка падает, если один из них
изменить без остальных.

Изменение лимита частоты — той же правкой `.env`, потому что переменная объявлена в `compose.yaml`,
и пересозданием службы:

```sh
docker compose up -d --force-recreate api
```

Пустое значение переменной для службы означает «применить объявленное в коде значение по
умолчанию», а не «снять ограничение». Приёмочные наборы строже: запускайте их через
`node --env-file=.env --test --test-concurrency=1 "scripts/acceptance/*.test.mjs"`; отсутствие
любого `*_ATTEMPTS` останавливает проверку, чтобы она не подставила вторую копию числа.

`SESSION_COOKIE_SECURE` разбирается как булево значение; `yes`, `on` и любая другая непонятная
строка останавливают процесс и называют переменную. Внутренние HTTP-клиенты также собираются только
с положительным таймаутом и пределом ответа: нулевой таймаут отвергается до первого запроса.

## 5. Эксплуатация

### Логи

```sh
docker compose logs --tail=100 api worker mailstub simulator migrate postgres frontend
```

Логи структурированные, с `request_id`; пароли, cookie, токены и строки подключения маскируются.
Worker раз в 30 секунд пишет `worker heartbeat` с числом доставленных и неудачных заданий, размером
очереди и возрастом самого старого задания.

Недоставленные задания очереди видны запросом:

```sh
docker compose exec -T postgres psql -U carsharing_migrator -d carsharing -c "SELECT id, kind, resource_id, attempts, last_error, next_attempt_at FROM outbox WHERE completed_at IS NULL ORDER BY next_attempt_at"
```

### Остановка и запуск отдельных процессов

Процессы независимы и переживают остановку друг друга:

| Команда | Что происходит |
| --- | --- |
| `docker compose stop worker` | API продолжает отвечать; задания остаются в очереди и доставляются после возврата |
| `docker compose stop mailstub` | письма остаются в очереди с ошибкой и повтором; после возврата приходит ровно одно |
| `docker compose --profile demo stop simulator` | парк остаётся там, где его застал последний тик |
| `docker compose restart` | данные сохраняются |
| `docker compose down` | данные сохраняются в томе `carsharing_postgres_data` |

### Обновление установки

```sh
git pull
```

```sh
docker compose up --build -d
```

`migrate` выполняется при каждом `up` и применяет новые миграции до старта API. Убедитесь, что он
завершился с кодом 0, а `/api/v1/health/ready` отвечает `200`. Состояние миграций отдельно:

```sh
docker compose run --rm migrate status
```

```sh
docker compose run --rm migrate up
```

Автоматического отката схемы намеренно нет. Перед опасной миграцией снимите резервную копию (§6):
восстановление из копии — предусмотренный путь отката, произвольный `down` — нет.

## 6. Резервная копия и восстановление

Копируются две вещи, и нужны они вместе: **дамп БД** и **каталог `.secrets/`**. Дамп без секретов
бесполезен — новый пароль не подходит к восстановленному тому.

Снять дамп:

```sh
docker compose exec -T postgres pg_dump -U carsharing_migrator -d carsharing --format=custom --file=/tmp/carsharing.dump
```

```sh
docker cp "$(docker compose ps -q postgres):/tmp/carsharing.dump" ./carsharing.dump
```

Восстановить в отдельную базу и сверить данные:

```sh
docker cp ./carsharing.dump "$(docker compose ps -q postgres):/tmp/restore.dump"
```

```sh
docker compose exec -T postgres psql -U carsharing_migrator -d postgres -v ON_ERROR_STOP=1 -c "CREATE DATABASE carsharing_restore"
```

```sh
docker compose exec -T postgres pg_restore -U carsharing_migrator -d carsharing_restore --no-owner --exit-on-error /tmp/restore.dump
```

Это тот же путь, который прогоняет приёмочная проверка `scripts/acceptance/restore.test.mjs`: она
снимает дамп теми же командами, восстанавливает его в базу-двойник (у неё это
`carsharing_restore_check`) и читает те же строки обратно — завершённую поездку, её счёт и её
письмо. Проверено на искусственных данных; в прогоне T18 дамп занял 7 059 832 байта.

Граница названа прямо: **восстановление поверх работающей базы этой сдачей не проверялось** —
проверенный путь ведёт в отдельную базу со сверкой. Дампы не коммитятся: `*.dump` исключён в
`.gitignore`.

Удалить базу-двойник после сверки:

```sh
docker compose exec -T postgres psql -U carsharing_migrator -d postgres -c "DROP DATABASE IF EXISTS carsharing_restore WITH (FORCE)"
```

## 7. Сброс установки

```sh
docker compose down -v
```

**Эта команда удаляет данные:** том с БД исчезает вместе с аккаунтами, поездками, счетами и
письмами. После неё чистая база мигрируется заново, а демонстрацию нужно ставить заново (шаг 5).
Для обычной остановки используйте `docker compose down` без `-v`.

Секреты `down -v` не трогает: они лежат в `.secrets/` на хосте.

## 8. Диагностика

| Симптом | Причина | Что сделать |
| --- | --- | --- |
| `port is already allocated` при запуске | занят порт 8080 или 8025 | измените `APP_PORT` в `.env` и повторите `up`; занятый порт ящика освободите на хосте |
| `DB_PASSWORD_FILE is required` или `cannot read ...` | отсутствует файл секрета | восстановите файл из локальной копии либо выполните setup в чистом каталоге |
| `database password must contain at least 32 characters; run setup` | секрет подменён вручную или повреждён | верните значение, созданное setup |
| API не поднимается, `migrate` вышел с ненулевым кодом | миграция не применилась | `docker compose logs migrate`; при повреждённой схеме — восстановление из копии (§6) |
| `/health/ready` отвечает `503 SERVICE_UNAVAILABLE` | БД недоступна | `docker compose ps postgres`, `docker compose logs postgres`; после возврата БД готовность восстанавливается сама |
| Письмо со счётом не приходит в ящик | заглушка остановлена | `docker compose up -d mailstub`; задание ждёт в очереди и доставится ровно одно |
| Нет предупреждения о конце брони | worker остановлен | `docker compose up -d worker`; просроченную бронь чтение текущей аренды снимает и без него |
| Машины не двигаются | симулятор не запущен — ожидаемое состояние | `docker compose --profile demo up --detach simulator` |
| Демонстрационная команда отклонена | запуск без профиля `demo` | добавьте `--profile demo`; `APP_ENV=demo` уже задан в `compose.yaml` |
| Вход отвечает `429` сразу нескольким людям | за опубликованным портом все браузеры машины приходят с адреса шлюза Docker, поэтому лимит по адресу общий | известная граница локального профиля; поднимите `RATE_LIMIT_SIGNIN_ADDRESS_ATTEMPTS` либо разведите проверки по времени |
| Залп одновременных входов отвечает `503` | ёмкость проверки пароля — два слота (`AUTH_ARGON2_CONCURRENT`) | известная граница; значение увеличивается в `compose.yaml` с учётом 19 МиБ памяти на один хеш |
| Данные пропали после остановки | выполнен `down -v` | том удалён безвозвратно; восстановление — из резервной копии (§6) |
| Сборка падает на ARM-машине | образ PostGIS закреплён для `linux/amd64` | потребуется эмуляция; случай отдельно не проверялся |

## 9. Границы этой установки

- **Публичного размещения нет.** Не входят: HTTPS и сертификаты, реальный домен, доверенный proxy с
  разбором цепочки адресов, реальные провайдеры оплаты и почты, KYC, Kubernetes, ARM.
- **Эмулировано:** оплата, почта, транспорт и подложка карты. Наружу не уходит ничего.
- **`SESSION_COOKIE_SECURE` выключен** — документированное исключение локального HTTP-профиля. При
  публичном размещении HTTPS обязателен, а эта настройка включается.
- **`postgres` не захарденен** так, как остальные службы: у него нет непривилегированного
  пользователя и корня только для чтения. Граница найдена аудитом T18 и принята для локального
  профиля.
- **Автоматического отката схемы нет**; путь отката — резервная копия.
- Полный перечень ограничений и непроверенного — `docs/T19-limitations.md`, границы готовности —
  `docs/SECURITY_AND_OPERATIONS.md` §6. Каталог `docs/` в Git не входит (решение D22/D37) и
  передаётся локальным пакетом сдачи; второго списка тех же фактов здесь нет намеренно.

Режим разработки с hot reload — это не установка, а рабочий профиль; он описан в README, раздел
«Разработка».
